# OPAirDrop

为 Android 手机接入 Apple AirDrop 的独立应用。以普通 APK 安装，不需要 Magisk 模块，也不改系统分区——需要的只是 root，以及一次驱动安装。收发本身全在应用里，不借任何框架。

唯一的框架依赖是可选的：**流体云卡片自己摊开**这一件事，由包内一个 LSPosed 模块（作用域 `com.android.systemui`）完成——它把系统算出来的 `remindType` 从 0 抬到 11，并让「本应用在前台」这道拦截器放行。启用它，卡片在文件到来时就摊开，应用正开着也照弹；不启用，收发自如同样成立，只是通知停在胶囊上，而且应用在前台时系统会把那张卡整张丢掉。

协议栈自己实现：mDNS 发现、BLE 广播唤起、TLS 1.3 握手与证书指纹钉住、`/Discover` `/Ask` `/Upload` 三个端点、cpio 归档与 DVZip 分块，全部在手机本地完成，不经过一加互传、Quick Share、Mosey，也不依赖任何 Google 服务。

## 功能

- **发送文件**：从系统分享面板选「发送到 iPhone」，或在首页点「发送文件」直接选文件（可多选）。面板在附近设备里列出 Apple 设备，点一下即发；对方确认后进度环按真实字节走，卡上那颗【取消发送】按下就断，页面上有同一颗。
- **接收文件**：打开后前台常驻，8770 端口在听、mDNS 与 BLE 广播同时在场，不需要停在任何页面上。iPhone 发起时通知上给「接受 / 拒绝」两个键，**60 秒**无人应答按放弃处理（`files/settings.conf` 里 `receive.decision_timeout_ms` 可改，5 秒到 5 分钟）——不替人做决定。接受之后进度卡上那颗键变成【取消接收】。
- **控制中心磁贴**：磁贴上的【AirDrop】就是接收开关，与首页「接收文件」那一行是同一份状态。开，服务在跑、端口在听、广播在发；关，三样一起停。没有十分钟到期这回事。
- **实时通知**：Android 16 起引入的实时通知跟着真实字节走，ColorOS 把它画在流体云的位置——形态是胶囊，点开是通知栏里那张卡。收完切成结果卡（可直接打开落盘目录），失败停在真实百分比而不是拉到满格，邀请给「接受 / 拒绝」两键。卡片走 `live_card_2` 渠道并申请提升为常驻，所以应用退到后台它也不会消失。摊不摊开由系统决定——要它在桌面态就展开，靠开头那个可选的模块。
- **内核驱动随包**：APK 自带四个内核模块、`wonder-ven` 与拉起脚本。功能页一键安装／卸载，装载前逐个校验 SHA-256，装完把脚本回执写在卡片上；卸载即恢复原厂驱动与网络环境。
- **按类型落盘**：照片与视频进 `DCIM/AirDrop`（相册直接扫得到），其余进 `Download/AirDrop`；也可以指定一个目录让所有文件都进去。同名不覆盖，默认加编号另存。
- **失败有话说**：对方拒绝、邀请过期、身份指纹不符、文件存不下，各是一句话，而不是一句笼统的「传输失败」。
- **三页界面**：首页给状态（传输、环境、设备信息），功能页给动作（驱动、射频、保存位置、设备显示），设置页只剩诊断与关于——日志级别、日志文件位置，以及源码、许可、版本信息与「检测更新」。超时与上限不在界面上了，改 `files/settings.conf` 即生效。设备名留空时用系统设备名（也就是蓝牙名称）对外自我介绍，不再退成机型。

## 适配基线

| 项目 | 当前配置 |
| --- | --- |
| 验证机型 | 一加 13（PJZ110），ColorOS V17.0.0 |
| Android | 17（API 37）；`minSdk 35`，`targetSdk 37` |
| 架构 | `arm64-v8a` |
| Root | 必需。KernelSU、KernelSU Next、APatch、Magisk 均可识别，首页直接报出管理器与版本 |
| 框架 | 可选。LSPosed（libxposed API 101+）加本应用模块、作用域 `com.android.systemui`，只用于流体云摊开；不装照样收发 |
| 无线 | Qualcomm WLAN 平台；AWDL 固定信道 149（5745 MHz），20 MHz 带宽、HT20、双空间流（`nss=2`） |
| 蓝牙 | 需要 BLE 广播：iPhone 要先在蓝牙上听到这条广播，才会把 AWDL 上的 AirDrop 服务拉起来。没有 BLE 的机器装得上，但发现不了对端 |
| 版本 | 1.0.0（versionCode 10000） |

驱动与射频是硬前提：接收要 `wonder0` 与 `awdltun0` 都在、8770 在听；发送要 `awdltun0` 上的组播出得去（mDNS 走的是这条隧道，不是 `wonder0`）。首页「环境」那一行给出 root 状态，功能页给出驱动状态（未安装 / 已就绪 / 一半 / 失败），两处都不靠猜。

三组权限各管一件事，缺了会缺得很有针对性。**一打开应用就把这三条一次问全**，只问从没问过的：问过又被拒的，系统不再弹框，缺口交给首页与磁贴上的状态胶囊和副标题去说——每次启动重问一遍只会把「被拒绝」演成「应用坏了」。发送页在缺权限时还会再补问一次。

- **通知**：接收状态、邀请确认、进度与结果。这条没开，接收端还在听，但邀请没有人能应答，等人应答的时长（默认 60 秒）走完按放弃处理。
- **附近的设备**（蓝牙广播与连接）：用 BLE 广播叫醒 iPhone。两条必须一起给——`BLUETOOTH_ADVERTISE` 决定能不能往外说，`BLUETOOTH_CONNECT` 决定能不能先看一眼自己的适配器，缺一条广播一次都不会注册。未授权时链路仍可被已经知道地址的对端连上，但发现不了新设备。
- **网络与组播**：发现与传输，安装即授予，无需操作。

## 驱动

随包的四个内核模块不是原厂的，也不是另找一个版本替换：**相对原厂只动了该动的地方，其余字节保持原样**。这一点每次装载前都会验一遍，不是「看着能跑」。

| 模块 | 改了什么 | 硬读数 |
| --- | --- | --- |
| `qca_cld3_peach_v2` | 开出一条 passthru 通路，把 802.11 帧的收发从固件手里交回主机 | 符号 CRC 588/588 与原厂逐条相同、0 条不符、0 条只存在于原厂；新增 12 条依赖全在 KMI 白名单里；导出 2 个符号给 provider；62 个 `passthru_*` 参数（原厂共 6 个参数，没有一个 passthru） |
| `mac80211` | 把 minstrel_ht 编进模块本身 | 原厂 `sun_perf.config` 根本没开速率控制，`wonder.ko` 因此注册不上（`Failed to select rate control algorithm` / `Ret: -2`）；现在 RC 符号 317→319（`+kmalloc_large`、`+param_ops_bool`），导出 136 条不变 |
| `wonder` | 新模块，`wonder0` 的驱动 | 装载后创建 IBSS `wonder0`：ch149 / 20 MHz / BSSID `00:25:00:ff:94:73` |
| `opairshare_wonder_provider` | 新模块，把 qca 导出的两个符号接到 wonder 上 | 缺它 `wonder_probe` 找不到 wiphy，`insmod wonder` 会报「registered no wiphy」 |

四颗的 `vermagic` 与原厂逐字符相同（`6.6.118-android15-8-o-4k SMP preempt mod_unload modversions aarch64`）。能顶掉原厂而**不是**替换文件，靠的是 `insmod` + 符号 CRC 一致：`/vendor` 分毫没动，`rmmod` 或重启即回原厂，这是这条路线唯一的回滚保证。

这些字节的源码就在同一仓库：`kernel-assets/source/`（仓库根目录）是上游的驱动覆盖层（46 个文件，`source-map.json` 逐条给出平台树落点）、9 个编号补丁（另有一个候选版 `0007-session-dp-candidate.patch`）和那串构建脚本。载荷清单、每个文件的 sha256、以及「从源码重建到哪一步了」都写在 [kernel-assets/README.md](kernel-assets/README.md)。一句话现状：**未打补丁的基线已经从官方源码复现过**（1359/1359 actions 全绿，`__versions` 588/588 与原厂一致，实机上 `rmmod` 原厂 → `insmod` 自建零报错、Wi-Fi 起来零丢包）；**打过补丁的这一颗也复现了，而且是逐字节的**——`pristine HEAD + 覆盖层 + 9 个补丁` 与实际构建树的 114 个改动文件比，112 个完全相同、0 个不同，余下 2 个是归档为「预期不复现」的死文件。复现脚本是 `tools/kernel/verify-reproduce.sh`，一行命令给出上面这组数字。

吞吐参数跟着脚本走，不留在谁的手输历史里。`tools/awdl-stack.sh` 把 22 项调优直接拼进 `insmod`，所以冷启动后的第一帧就是按这些数字发的；同一个列表在链路起来后还会再写一遍并逐项读回，覆盖那三条不走重载的路径——本 boot 已经换过栈、只跑 `link`、以及旧脚本留下的模块。读回对不上会打印 `TUNING_MISMATCH`，而不是安静地跑慢一点。其中 `nss=2` 是关键的一项：3.2 MB/s 那一轮实测就是双流，而脚本此前从未设过它，所以更早的实验都在单流上半速空口。

## 使用入口

第一次使用：

1. 安装 APK 并打开。启动时会把三条权限一次问全——通知、附近的设备（蓝牙广播与连接），全给；给过之后不再打扰。
2. 看首页「环境 → root 权限」：显示「已获取」，副标题是授权管理器与版本；显示「未获取」就去管理器里给本应用授权。
3. 进功能页 → 驱动 → 【安装】。约半分钟，中途 Wi-Fi 会断一下（驱动不能在 Wi-Fi 活着时替换）。装好后右边胶囊变「已就绪」。
4. 在控制中心编辑页把【AirDrop】拖进快捷开关并点亮；或者回首页点「接收文件」那一行的胶囊。
5. 在 iPhone 上把 AirDrop 设为「所有人」（控制中心里那项，10 分钟有效），屏幕保持解锁亮着；从相册或文件里选文件分享，在列表里选本机，本机通知上按「接受」。
6. 可选：到 LSPosed 里启用本应用的模块，作用域勾上「系统界面」。不勾也能收发，只是卡片停在胶囊上，且本应用在前台时那张卡会被系统丢掉。

### 接收

接收端一次只服务一台设备，第二台排队，不会两路同时往同一个目录里写。接受之后进度同时出现在通知与实时通知上；收完的结果卡片写清楚文件名、大小、落在哪个目录。

拒绝与超时在发送端看来都是失败，在本机是两句话：拒绝是「已拒绝」，超时是「邀请已过期」。后者刻意不写成拒绝——没人看见这条邀请，不等于他拒绝了你。

### 发送

两条入口，一条路径：系统分享面板，或首页「发送文件」的文件选择器。选完之后都交给同一个发送页。

面板先显示「正在搜索附近设备……」，设备出现后点头像，等对方在 iPhone 上确认，环走完写「发送完成」。发送不需要本机处于接收状态，也不需要打开接收开关——那是接收端的事，发送端不欠它任何前提。

### 保存位置

| 收到的东西 | 落在哪 |
| --- | --- |
| 照片、视频 | `DCIM/AirDrop` |
| 其余一切：文档、压缩包、安装包、无扩展名的文件 | `Download/AirDrop` |
| 功能页「接收文件保存位置」填了目录 | 全部进那一个目录，不再分类型 |

同名文件默认并排留两份（`IMG_0001.jpg` 与 `IMG_0001 (1).jpg`），不覆盖。卡片上报的是落盘后回查到的真名，不是提交时的名字——所以加了编号也照实说。

## 已知限制

- **只在一加 13 上验证过。** 换机型要换随包的驱动与补丁，不是改一个设置就能跑。
- **Wi-Fi 共享射频只在 AP 位于 149 信道时能收发。** AWDL 的 tap 被驱动钉在 149（`opairshare_pas_rx_fixed_channel()` 对其他频率直接 `-EOPNOTSUPP`，这个数字在驱动里硬编码了四处），而 iPhone 的 AWDL 跟随它自己连着的那个 AP。AP 在别的 5G 信道时两边永远不同频：Wi-Fi 上得去，AirDrop 看不见人。要根治得让 tap 跟随 STA 信道，属驱动改动，还没做（取样与四步验收写在 `Plan.md` §8.4）。临时办法是把路由器的 5G 定到 149。
- **iPhone 那边有两件事要做**：控制中心把 AirDrop 设为「所有人」（10 分钟有效），屏幕保持解锁亮着——锁屏后 iPhone 会暂时离开这条直连链路。本机这一侧同时发 mDNS 公告与 BLE 广播去叫醒它；实测从 iPhone 点开分享面板到本机出现在列表里约 1 秒（更早一轮里蓝牙判决借过主线程，空窗 77 秒，已修）。
- **速度由对端决定，不是本机的上限。** 发送稳态 **3.24 MB/s**（24.7 MB 视频，后 6 秒；峰值 3.48，全程 2.59），接收 857 kB/s（iPhone 13 / iOS 27；在 Xs Max 上只有 0.1 MB/s，那是对端 24.45 ms 的固定节拍，不在本仓库）。发送的单流天花板是 **5.05 MB/s**，算式是 iPhone 通告的 89 KB 接收窗口 ÷ 每聚合往返 17.2 ms；实测 3.24 MB/s 只用掉其中 64%，差的那部分在 TCP 慢启动与 1.5% 的重传里，不在空口。要更高只能并行多条 TCP 流。
- **10 MB/s 到不了，而且不是靠改信道宽。** AWDL 的社交信道固定 20 MHz @ 5745，加宽会直接掉出对端协商的信道；瓶颈是对端的通告窗口，不是带宽。这条路线上的现实顶在 8~9 MB/s 一带，且必须多流摊开。
- **每次重启后要重装一次驱动**（约半分钟）。应用没有开机自启，重启后需要重新打开接收；重装会把随包的那套吞吐参数一并带回来，不需要再手工往 sysfs 里写。
- **证书指纹「相符也照常发」那一支还没在真实 iPhone 上走过。**「不符就拒」已经用错误指纹的握手验过，能给出可读原因。
- 多文件、超大文件、锁屏状态、传输中断电这些场景还没有全覆盖。
- 尚未发布正式 Release，也没有上架任何应用商店。

## 项目结构

```text
repo-src/
├── crates/            Rust 协议栈，八个 crate，协议知识只在这里
│   ├── bplist/        Apple 二进制 plist 读写
│   ├── cpio/          cpio odc/newc、DVZip 分块、gzip 识别
│   ├── mdns/          DNS 报文编解码
│   ├── http/          双向流式 HTTP/1.1 解析
│   ├── awdl/          AWDL 数据面、/dev/tun 与 AF_PACKET、awdld 守护进程
│   ├── airdrop/       三端点语义、客户端、服务端、收件箱
│   ├── settings/      参数表：键、区间、文案三合一
│   └── ffi/           C ABI 与 JNI，Java 侧唯一入口
├── android/           Android 应用
│   ├── app/           三页界面、发送页、接收服务、磁贴、驱动安装
│   └── build.sh       一条命令出 APK：先 Rust，后 Gradle
├── kernel-assets/     随包内核模块、驱动源码覆盖层与拉起脚本（仓库根目录）
├── tools/             链路拉起、抓包与真机自测脚本
├── CHANGELOG.md
└── LICENSE
```

界面没有 XML 布局，全部代码绘制；`dependencies` 里只有一条 `compileOnly 'io.github.libxposed:api:102.0.0'`，编那个可选的流体云模块用，不进包——没有 AndroidX、没有 Kotlin，APK 里只有框架类和那一个 `.so`。`crates/ffi/jvm` 下的 Java 类与 `android/app` 一起编进 APK。

## 开发入口

在仓库根目录：

```sh
# 出包：先交叉编译 aarch64 的 Rust，再打 APK
bash android/build.sh assembleDebug
bash android/build.sh clean

# 全量测试
cargo test --workspace          # 431 passed / 0 failed（1 ignored）
bash crates/ffi/jvm/check.sh    # 394 条 ok，桌面 JVM + -Xcheck:jni
```

JDK、SDK 与 Gradle 都放在 `tools/` 下，脚本按名字取而不查 `PATH`，可以用 `JAVA_HOME`、`GRADLE_BIN`、`CARGO_BIN` 覆盖。真机脚本在 `tools/`：`awdl-stack.sh` 拉起链路，`capture.sh` 抓隧道上的包，`tap.sh` 在 802.11 那一侧再抓一份（两者一比才知道是「对端没发」还是「我们收丢了」），`awdld-probe.sh` 看守护进程状态。

日志默认按 `debug` 记（`log.level`），一天一个文件写在 `Documents/AirDrop/airdrop-YYYY-MM-DD.log`——追时序的时候不用先去改设置，嫌吵在设置页调回 `info` 即可。
